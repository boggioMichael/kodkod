# שיעור 6 · סגירת גרסאות והצגות

## מהלך המפגש

המפגש האחרון הוא רצף אחד של 255 דקות: שחרור גרסה, הצגות וסיכום. הזמנים כאן מניחים שישה צוותים. עם פחות צוותים, הזמן שמתפנה עובר ל-review בין צוותים.

| דקות | חלק | מה קורה |
| --- | --- | --- |
| 0-45 | הקפאה ושחרור | PRs אחרונים עד דקה 30, ואז tag ו-Release |
| 45-55 | הפסקה | |
| 55-145 | הצגות | 15 דקות לצוות: 10 הצגה ו-5 שאלות |
| 145-160 | הפסקה | |
| 160-220 | review בין צוותים (רשות) | כל צוות עושה fork לריפו של צוות אחר, פותח שני issues ו-PR אחד עם הצעה, והצוות המארח סוקר |
| 220-255 | סיכום הקורס | מה היה הכי קשה, משוב לצוותים, והמשך למידה עצמית |

### שחרור הגרסה (0-45)

```
git switch main && git pull
git log --oneline --first-parent main     # כל שורה מפנה ל-PR
git tag -a v1.0 -m "zit v1.0"
git push origin v1.0
```

אחר כך פותחים GitHub Release מה-tag, עם הערות שחרור.

הבדיקה שלך בכל ריפו נמשכת דקה. ברירת המחדל של GitHub מוסיפה את מספר ה-PR לכותרת של squash, ול-merge commit משמו של ה-PR. לכן בצוות שבחר באחת משתי השיטות האלה, שורה ב-`--first-parent` בלי מספר PR היא ככל הנראה commit שעקף את התהליך.

## מבנה ההצגה ושאלות לצוותים

כל צוות מציג 10 דקות במבנה קבוע, וחצי מההצגה הוא git חי ולא שקפים.

1. **הבעיה (דקה).** במילים של הצוות, מתוך ה-README.
2. **הארכיטקטורה (3 דקות).** התרשים מ-`docs/architecture.md`, ומסלול של `zit checkout` מתחילתו ועד סופו.
3. **הפיצ'ר המיוחד (2 דקות).** בעיה, פתרון, ודוגמת שימוש בטרמינל.
4. **סיור בריפו (3 דקות).** `git log --oneline --graph`, PR עם דיון review אמיתי, קונפליקט שפתרו, וה-tag.
5. **מה הלאה (דקה).** מה ממומש, אם בכלל, ומה היו עושים בשבוע נוסף.

שאלות לשאול את הצוותים:

- המחשב היחיד שמחזיק קובץ כבוי. מה קורה ב-`zit checkout`?
- איך אתם יודעים שהקובץ שהגיע ממחשב אחר לא שונה בדרך?
- כמה מקום בדיסק תופס אצלכם checkout של ריפו עם מיליון קבצים?
- איזו החלטת תכנון (ADR) הייתם משנים היום, ולמה?
- איזה PR היה הכי קשה לסגור?
- תראו לי מי כתב את השורה הזו, ובאיזה PR. (`git blame`, ואז ה-PR ב-GitHub)
